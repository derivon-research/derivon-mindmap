结论（一句话）

把会话自己的进程放进系统沙箱，而不是把工具执行路由进沙箱。macOS 零授权、零体积；Windows 走免管理员的受限令牌。

5 · 代价（实测）

读法：只有「把 bash 工具路由进沙箱」这条路才付每调用一次的启动钱；把会话进程放进沙箱是一次性的。 profile 编译费随规则数超线性增长（1 条 ~11 ms，500 条 ~149 ms），所以规则不能随文件数增长。

6 · 候选机制 × 判据

候选保证强度需要管理员？覆盖子进程/后代覆盖技能脚本与进程内扩展机器变更 / 可逆性体积与启动
0. 今天：工具授予 + tool_call 守卫无（护栏）否否否（技能脚本压根不进守卫）无0
1. Node 层（--permission / vm / isolated-vm / WASI）无（官方文档自称不是安全机制）否否否无0
2. 只路由 bash 工具（settings.shellPath）部分：只有 shell 那一支否是（该支）否（实测技能脚本照写）一个 wrapper + 一份 profile每次工具调用 +6~16 ms
3. 路由每一个 spawn 点部分：spawn 点是开放集合否是部分（进程内 writeFileSync 仍在外面）改多处调用点同 2
4. 会话进程进系统沙箱（推荐）强：该进程树写不进工作区否（macOS 零授权 / Windows 免管理员档）是是一份 profile，删掉即回退0 体积；启动 +~6 ms；每模式多一个进程 ≈ +120 MB
5. 整进程进容器 / 微虚拟机最强（还能收读取）macOS 否 / Windows 需 WHP 或提权是是引入运行时依赖+100 MB~GB；每会话 VM 启动 0.5~2 s；凭据随进程进沙箱
6. Windows 免管理员档：受限令牌 WRITE_RESTRICTED强（写侧）否是是无机器变更需 Rust 原生代码
7. Windows 强化档：Codex 式账户 + 防火墙 + DACL最强（还能收读取）是（一次性 UAC）是是本地账户 / 防火墙 / 登录项，卸载路径要专门做重；企业策略下会失败

7 · 三条边界（票里 AC 第四条要的东西）

  1. 覆盖：被沙箱的那个会话进程树内的一切文件写入 —— companion 自己的代码、命令面技能脚本（子进程）、shell 工具及其全部后代；对工作区的写、重命名、删除、chmod、xattr 都在系统层失败；符号链接、硬链接、firmlink 别名、.. 拼写与嵌套 sandbox-exec 都不构成逃逸。
  2. 不覆盖 —— 进程内扩展：它跑在被沙箱的进程里，所以它的文件写入被覆盖；但它的读取、网络、以及它手里的模型凭据不受限（ADR-0010 已写明这是「操作者自己的代码，带着操作者的凭据」）。要收读取，只有容器/VM（形态 5）或 Windows 强化档 / AppContainer。
  3. 不覆盖 —— 凭据：留在宿主、留在 companion 进程内。进程级沙箱不搬运凭据；把进程放进容器才会把凭据带进去。
  4. 不覆盖 —— 宿主的其它路径：L1 完全不覆盖（rm -rf ~ 仍可）；L2 覆盖写入，但不覆盖读取 —— 整个文件系统仍可读，包括 ~/.ssh。
  5. 不覆盖 —— 网络：不覆盖，且必须允许（模型调用、tavily-cli）。
  6. 不覆盖 —— macOS TCC 与签名：seatbelt 子进程默认继承宿主 app 的 TCC 身份，所以给 app 授权（Full Disk Access / 辅助功能）等于给沙箱里的会话授权；这条要写进 ADR。
  7. 不覆盖 —— 创作侧与宿主应用自身：创作侧不沙箱（写工作区是它的职责）；Rust 宿主、webview、命令面之外的写入不在沙箱里，它们不是 agent。
  8. 与既有 ADR 的一致性：ADR-0010 的「一个 companion 进程服务整个应用」必须改成按模式一个进程；ADR-0011 要补一句「学习侧另有一层系统层保证，管的是工作区（L1）或几乎所有写入（L2）」；新立 ADR-0014 把「沙箱 / 外部隔离 / 平台授权 / 护栏」四个词分开。
